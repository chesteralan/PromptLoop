# Abstraction Rules: UI Primitives

**Files:** All `src/components/ui/*.tsx`

```
input.tsx       button.tsx      table.tsx       card.tsx
input-group.tsx dropdown-menu.tsx  select.tsx      textarea.tsx
tooltip.tsx     tabs.tsx        switch.tsx      skeleton.tsx
sheet.tsx       separator.tsx   scroll-area.tsx progress.tsx
label.tsx       dialog.tsx      command.tsx     badge.tsx
avatar.tsx
```

---

## Overview

All UI primitive files are auto-generated by **shadcn/ui** (`components.json` confirmed present). They follow a consistent pattern:

- `forwardRef` wrapping
- `cn()` class merging via `clsx` + `tailwind-merge`
- `cva()` (class-variance-authority) for variants
- `Radix UI` primitives as base

These files are **already well-layered** — they are pure presentation with zero business logic, no data access, and no IPC calls.

---

## Current Layer Mix

### Good

- ✅ Zero business logic — all UI primitives are purely presentational.
- ✅ Zero data layer coupling — no Firestore, no Electron API, no hooks.
- ✅ Consistent pattern across all files — generated from shadcn/ui template.
- ✅ Proper accessibility attributes (`aria-*`, `role` attributes).

### Minor Issues

- ⚠️ `input-group.tsx`, `input.tsx`, `textarea.tsx`, `select.tsx` all serve similar "form input" purposes — could be consolidated into a single `FormInput` with `as` prop.
- ⚠️ Some components (e.g., `dialog.tsx`, `sheet.tsx`) are large generated files with deeply nested Radix primitives, making manual overrides fragile.

---

## Extraction Opportunities

### Minimal — these are already at the right abstraction level.

### Potential consolidations:

- **`cn()` utility** is imported in many files — already centralized in `src/lib/utils.ts`. ✅
- **Radix + cva pattern** could have a `createPrimitive(name, root, variants)` factory to reduce boilerplate, but shadcn's explicit exports are more maintainable.
- **Type re-exports** — several files re-export types from `@radix-ui/*` — could consolidate into a single `ui/types.ts`.

---

## Interface Suggestions

### Already well-typed:

- All components use proper TypeScript with `forwardRef`, `React.HTMLAttributes`, and Radix component props.
- `Button` uses `cva` with typed `VariantProps`.

### Suggestions:

- Add `data-testid` prop support to all components for testing.
- Consider a shared `UIComponentProps` interface: `{ className?: string; children?: ReactNode }`.

---

## Dependency Direction

### Clean:

- ✅ All UI primitives depend only on `react`, `clsx`, `tailwind-merge`, `class-variance-authority`, `@radix-ui/*`, and `lucide-react` (for icons).
- ✅ No circular dependencies — UI primitives do NOT import from components, hooks, stores, or lib (except `cn`).
- ✅ All business-level components import from `../ui/*` — correct direction.

---

## Duplication

### Intentional — shadcn/ui generates duplicated boilerplate per component:

- `cn()` import + usage pattern in every file.
- `forwardRef` signature repeated.
- Radix pattern: `Root` + `Trigger` + `Content` etc. duplicated per component.
- `displayName` assignment repeated.

### Acceptable duplication tradeoff:

- Each file is self-contained and independently replaceable.
- Upstream shadcn updates can be applied per-file without conflicts.

---

## Constants/Magic Values

### Minimal — most class names are parameterized via `cva` or passed as `className`:

- `'h-9 w-9'` (small button size default).
- `'bg-primary'`, `'text-primary-foreground'`, etc. are Tailwind theme tokens.
- No hardcoded business values — only design tokens and layout classes.

### Notable:

- `'ui-button'`, `'ui-dialog'`, etc. (some Radix components use `data-state` attributes that are string constants).
- Skeleton dimensions like `'h-4 w-full'` are hardcoded but intentionally flexible via className pass-through.
